## Objetivo

Implementar el adaptador `HolderLookup` (interfaz + implementacion `mock` seleccionable por
entorno) que valida titular y CCI de una cuenta destino, para que la transferencia a tercero e
interbancaria (`E2-T09`) no invente el titular ni confie en datos que envia el cliente.

## Alcance

- **Incluye:** interfaz del adaptador, implementacion `mock` deterministica, seleccion por
  variable de entorno (`HOLDER_LOOKUP_PROVIDER=mock|http`), timeouts/reintentos/circuit breaker,
  endpoint interno de validacion consumido por `E2-T07`/`E2-T09`, cache opcional por CCI.
- **No incluye:** contrato real con el equipo par (se usa simulador, D01), la saga
  (`E2-T09`), el alta de beneficiarios (`E2-T13`), la UI (`E2-T11`).

## Contexto embebido (decisiones que aplican)

- Adaptadores externos simulados viven en `app/adapters/` con interfaz comun e implementacion
  `mock` activable por configuracion; el proveedor real se agrega despues sin tocar el dominio
  (`docs/02#9`).
- Circuit breaker + timeouts: reintentos con backoff; nunca bloquear el hilo indefinidamente
  (`docs/02#8`).
- El contrato interbancario no existe aun: se usa un simulador con contrato propio (`docs/17#1`
  D01, `docs/01` contradiccion 9).
- Anti-enumeracion en lookup: no revelar si un CCI/titular existe fuera de la operacion; mensajes
  neutros y sin eco del dato consultado (`docs/05#6.1` patron del lookup KYC, `docs/15#3`).
- Sin PII/secretos en logs; el cliente jamas ve la API key del proveedor (`docs/02#10`).

## Modelo de datos

Sin tabla nueva obligatoria. Si se decide cachear validaciones, usar un cache en memoria/Redis
(sin ORM) o registrar en `transactions.metadata` solo el resultado booleano; nunca persistir el
CCI en claro. `beneficiaries.account_or_cci` (`docs/03b#53`) se cifra en `E2-T13`, no aqui.

## API / eventos

- **Endpoints:** ninguno publico (**D-07**). Se expone una **funcion de fachada** en
  `transactions/service/`
  `validate_holder(cci, holder_name?, bank_code?) -> {valid, holder_name_masked}` consumida por
  `E2-T09`/`E2-T07`. El endpoint `POST /transfers/interbank/validate` queda **retirado** (era
  inventado y no esta en `docs/05#6.3`); no se crea ni se documenta en OpenAPI.
- **Eventos emitidos:** ninguno propio (la operacion de dinero la emite `E2-T07`/`E2-T09`).
- **Eventos consumidos:** ninguno.
- **Errores de negocio:** `HOLDER_LOOKUP_UNAVAILABLE` (503), `HOLDER_NOT_FOUND` (404 neutro),
  `VALIDATION_ERROR` (formato de CCI: 20 digitos; `docs/05`), `429 RATE_LIMITED`.

## Reglas de negocio

- CCI valido = 20 digitos numericos; banco destino codificado segun `bank_code`; validacion antes
  de mover dinero.
- El `mock` es determinista por CCI (mismo CCI -> mismo resultado) para pruebas reproducibles,
  como parte del **simulador interbancario `D01`** (`docs/17#1`; `D09` es el score de central de
  riesgo simulada y no aplica aqui).
- Reintentos con backoff y circuit breaker; timeout configurable
  (`HOLDER_LOOKUP_TIMEOUT_SECONDS`, default 5 s; `HOLDER_LOOKUP_MAX_RETRIES`, default 2).
- Mensajes neutros: no revelar existencia ni titular completo; devolver titular enmascarado.
- Cualquier umbral/timeout es configurable por entorno o `config.parameters` (dueno
  `shared/config`); sin constantes cableadas de negocio.

## Criterios de aceptacion (CA)

- `CA-02` de HU06: el CCI/titular se valida antes de enviar la transferencia interbancaria.
- Proveedor caido/reintentos agotados -> error neutro, sin bloquear el hilo ni filtrar datos.

## Pruebas requeridas

- Camino feliz: CCI valido + titular coincidente -> `valid: true`.
- Errores: CCI con formato invalido -> `422`; CCI inexistente -> `404` neutro; proveedor caido ->
  `503`; reintentos agotados; circuit breaker abre y se recupera.
- Idempotencia/anti-enumeracion: el mismo CCI inexistente devuelve siempre el mismo error sin
  distinguir "no existe" de "no disponible"; sin PII en logs.
