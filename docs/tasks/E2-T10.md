## Objetivo

Generar el comprobante de una transferencia (`GET /transactions/{id}/receipt`) en PDF con fecha,
montos, cuentas enmascaradas y un numero de operacion unico y verificable, sin exponer PII y sin
inventar datos contables.

## Alcance

- **Incluye:** caso de uso de comprobante, numero de operacion unico (derivado del
  `transaction_id`/`journal_entry_id`, no secuencial adivinable), render PDF, endpoint con
  control de propiedad/RBAC, plantilla con datos minimos.
- **No incluye:** envio por correo (`notifications`, HU22), export de movimientos de cuenta
  (`E2-T03`, ya `Hecho`), firma digital del comprobante, UI (`E2-T11`).

## Contexto embebido (decisiones que aplican)

- Datos sensibles enmascarados por defecto; el numero completo de cuenta nunca sale del modulo
  (`docs/02#10`, `docs/16#2` regla 9; patron ya usado en `accounts.service.mask_account_number`).
- Sin PII en logs (`docs/16#2` regla 7).
- El comprobante es una vista de lectura: no recalcula saldos ni crea asientos; la fuente de
  verdad es `ledger`/`transactions` (`docs/03c#14`).
- Dinero entero en centimos; fechas ISO-8601 UTC (`docs/05#1`).
- Sin dependencias nuevas si una libreria PDF ya esta disponible; si no, documentar el 501 y
  degradar (patron `E2-T03`). Preferir stdlib o una lib ya presente.

## Modelo de datos

Lee `transactions` (`id`, `type`, `status`, `amount_minor`, `fee_minor`, `currency`,
`created_at`, `settled_at`, `external_ref`), `transaction_status_history` y el `journal_entry`
asociado via `ledger.service` (fachada). No crea tablas nuevas.

## API / eventos

- **Endpoint:** `GET /api/v1/transactions/{id}/receipt` -> PDF (`application/pdf`) o `501
  RECEIPT_FORMAT_NOT_SUPPORTED` si no hay backend PDF disponible. Solo lectura; sin
  `Idempotency-Key`.
- **Eventos emitidos:** ninguno (documento de lectura). Opcional `notification.sent` via fachada
  si se decide enviar copia (fuera de alcance).
- **Eventos consumidos:** ninguno.
- **Errores de negocio:** `NOT_FOUND` (transaccion inexistente), `NOT_AUTHORIZED` (ajena),
  `409`/`VALIDATION_ERROR` si la transaccion no esta en estado emitible
  (`SETTLED`/`POSTED`/`CONCILIATED`), `501` si no hay lib PDF.

## Reglas de negocio

- Numero de operacion unico: derivado determinista del `transaction_id` (p. ej. prefijo + UUID o
  hash corto), estable entre reintentos y no adivinable/secuencial.
- El comprobante solo se emite para transacciones efectivamente ejecutadas; para `REJECTED`/
  `FAILED` devolver `409`/`VALIDATION_ERROR` (no emitir comprobante de dinero no movido).
- Mostrar cuentas enmascaradas (`****1234`), montos en centimos, moneda, tipo, fecha/hora UTC,
  numero de operacion y estado.
- No incluir documento, CCI completo ni datos del titular sin enmascarar.

## Criterios de aceptacion (CA)

- `CA-04` de HU06: al finalizar, el cliente obtiene comprobante con fecha, montos, cuentas y
  numero de operacion.
- El numero de operacion es unico por transaccion y se mantiene estable.
- Ninguna respuesta/log filtra PII.

## Pruebas requeridas

- Camino feliz: transferencia `SETTLED` -> PDF valido con numero de operacion y montos correctos.
- Errores: transaccion inexistente -> `404`; ajena -> `403`; rechazada/fallida -> `409`;
  sin lib PDF -> `501`.
- Concurrencia/idempotencia: dos llamadas al comprobante devuelven el mismo numero de operacion y
  no crean asientos ni filas nuevas.
