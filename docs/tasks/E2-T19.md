## Objetivo

Exponer `POST /api/v1/transactions/{id}/authorize` para que el cliente envie la firma biometrica del
`nonce` de un pago sensible en `PENDING_AUTHORIZATION`; al validarla, el motor continua
(`AUTHORIZED -> FUNDS_HELD -> POSTED -> SETTLED`) y responde el resultado; si falla, rechaza sin
mover dinero.

## Alcance

- **Incluye:** endpoint, esquema de request (`nonce`, `signature`, `device_id`), validacion
  RBAC/propiedad, consumo del `nonce` de un solo uso, transicion de estados, `Idempotency-Key`,
  contrato OpenAPI y errores.
- **No incluye:** el mecanismo interno de verificacion (`E2-T17`), el umbral/perfiles (`E2-T18`),
  la UI (`E2-T21`), la notificacion al fallo (`E2-T20`).

## Contexto embebido (decisiones que aplican)

- Endpoint de dinero: `Idempotency-Key` obligatoria; misma clave + mismo cuerpo = mismo resultado
  (`docs/04#5`, `docs/05#3`).
- Solo el motor cambia de estado; cada cambio deja fila en `transaction_status_history`
  (`docs/04#3`).
- La transaccion debe estar en `PENDING_AUTHORIZATION`; en otro estado -> `409 Conflict`
  (`docs/05#5`).
- La firma se verifica contra la clave vigente del binding; error generico sin oraculo
  (`docs/05#6.1` decision E1-T42, R26).
- Sin logica en el router: valida, traduce y delega al `service/` (`docs/05#1`).
- Respuesta `{"data", "meta"}`; errores problem+json (`docs/05#4`). Sin PII/secretos en logs.

## Modelo de datos

Lee/actualiza `transactions.status`/`version`/`settled_at` y `transaction_status_history`
(`docs/03b#61`, `#62`). El `nonce` se consume via la fachada de `identity` (sin copiar sus
tablas). No crea tablas.

## API / eventos

- **Endpoint:** `POST /api/v1/transactions/{id}/authorize` -> `200 {data: {transaction_id, status}}`.
  `Idempotency-Key` obligatoria.
- **Eventos emitidos:** `funds.held`, `transfer.settled` (al continuar); el fallo lo emite
  `E2-T20` (`auth.failed_attempt`/`fraud.alert.raised`).
- **Eventos consumidos:** ninguno.
- **Errores de negocio:** `NOT_FOUND`, `NOT_AUTHORIZED` (no es el titular/firma invalida, generico),
  `EXPIRED_NONCE`, `CONFLICT` (estado distinto de `PENDING_AUTHORIZATION`; idempotencia con cuerpo
  distinto), `VALIDATION_ERROR` (payload malformado).

## Reglas de negocio

- Solo el titular de la transaccion puede autorizarla (RBAC por `initiator_user_id`/cuenta origen).
- El `nonce` es de un solo uso y con TTL; reutilizarlo -> `EXPIRED_NONCE`/`NOT_AUTHORIZED`.
- Firma valida + estado correcto -> avanza exactamente una vez; reintento idempotente devuelve el
  mismo resultado sin re-asentar.
- Firma invalida -> no cambia saldos ni crea asiento; registra evento de seguridad.
- El endpoint no recalcula el umbral (lo decidio `E2-T17`); solo completa la autorizacion.

## Criterios de aceptacion (CA)

- `CA-01` de HU08: el pago sobre el umbral no se completa sin biometria valida.
- `CA-04` de HU08 (parcial): un intento fallido no debita y queda trazable (el bloqueo preventivo
  `CA-02` de HU08 lo aplica `E2-T17`, no este endpoint).
- Idempotencia: doble llamada no duplica el asiento.

## Pruebas requeridas

- Camino feliz: `PENDING_AUTHORIZATION` + firma valida -> `SETTLED` con asiento cuadrado.
- Errores: firma invalida -> rechazo sin movimiento; `nonce` expirado; estado incorrecto -> `409`;
  transaccion ajena -> `403`; transaccion inexistente -> `404`.
- Concurrencia/idempotencia: dos `authorize` concurrentes -> un solo asiento; misma
  `Idempotency-Key` -> misma respuesta.
