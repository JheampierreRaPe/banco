## Objetivo

Definir el adaptador `ClearingSource` que entrega **archivos de compensacion simulados** (lote de
operaciones de la red/equipo par) con una interfaz comun, una implementacion `mock` determinista y
una `http` con timeout/reintentos/circuito, sin persistir nada y sin mover dinero. Es el cimiento de
la ingesta de HU19.

## Alcance

- **Incluye:**
  - Interfaz `ClearingSource` con `fetch_files(*, since=None, source=None) -> list[ClearingFilePayload]`
    y `fetch_items(file_ref) -> list[ClearingItemPayload]` (o un unico `fetch_batch`).
  - `MockClearingSource` determinista (sin red): genera lotes reproducibles con `file_ref`,
    `checksum` SHA-256, `item_count`, items con `external_ref`, `amount_minor`, `currency`,
    `value_date`, `direction` (`INBOUND`/`OUTBOUND`) y `raw`.
  - `HttpClearingSource` con `GET {base_url}/clearing/files` y `GET {base_url}/clearing/files/{ref}/items`,
    timeout corto, reintentos con backoff y circuito; la key solo en cabecera `Authorization`.
  - Fabrica `create_clearing_source()` por `CLEARING_SOURCE_PROVIDER` (`mock` por defecto; valor no
    reconocido -> `mock`), siguiendo `docs/02#9`.
  - Errores tipados `CLEARING_SOURCE_UNAVAILABLE` (`503`) y `CLEARING_SOURCE_TIMEOUT` (`502`).
- **No incluye:** tablas, migraciones, ingesta, matching, excepciones, endpoints, jobs ni UI
  (eso es `E5-T17`..`E5-T21`). No valida contra un banco real ni define el contrato del equipo par.

## Contexto embebido (decisiones que aplican)

- **Patron de adaptadores (`docs/02#9`):** todos viven en `backend/app/adapters/`, con interfaz
  comun y `mock` activable por configuracion; el proveedor real se agrega sin tocar el dominio.
- **Contrato de clearing (`docs/04#8`):** la conciliacion compara `transactions`/`journal_entries`
  contra `clearing_items`; la coincidencia es por referencia externa, monto, moneda y fecha.
- **Datos (`docs/03b#12.1`):** `clearing_files` (`source`, `file_ref` UQ, `checksum`, `item_count`,
  `status`) y `clearing_items` (`external_ref`, `amount_minor`, `currency`, `value_date`,
  `direction`, `status`, `raw`). El adaptador **no** escribe esas tablas; solo entrega payloads.
- **Simulacion:** el equipo par puede no existir (`D01`); el mock cubre el MVP y el http queda listo
  para cuando publique su contrato.
- **Seguridad:** sin PII ni secretos en logs; la API key nunca va en URL, query ni repositorio.
- **Dinero:** montos enteros en centimos (`int`), nunca `float`; el adaptador no mueve dinero.

## Reglas de negocio

- `file_ref` es unico por lote; `checksum` SHA-256 del contenido canonico; `item_count` debe
  coincidir con los items entregados.
- Montos `> 0` en centimos; moneda ISO-4217 de 3 letras; `direction` solo `INBOUND`/`OUTBOUND`.
- El mock es determinista: misma entrada -> mismo lote/checksum (pruebas reproducibles).
- El http nunca bloquea indefinidamente: timeout + reintentos + circuito; un fallo se traduce a
  error tipado, no a `500` generico.
- Sin red en pruebas: el http se prueba con transporte inyectado/mockeado.

## Criterios de aceptacion (CA)

- `CA-01`: existe la interfaz y la fabrica; `CLEARING_SOURCE_PROVIDER=mock` devuelve un lote
  determinista con `file_ref`, `checksum` e items validos.
- `CA-02`: el http aplica timeout, reintentos y circuito, y traduce fallos a
  `CLEARING_SOURCE_UNAVAILABLE`/`CLEARING_SOURCE_TIMEOUT`.
- `CA-03`: payload invalido (monto <= 0, moneda mal formada, `item_count` inconsistente) se rechaza
  sin efectos y sin red.
- `CA-04`: `ruff`/`black` limpios y `pytest` en verde; sin PII/secretos en logs.

## Pruebas requeridas

- Camino feliz: mock entrega lote + items; checksum estable entre llamadas.
- Errores: item con monto <= 0 / moneda invalida / `item_count` distinto -> error de validacion.
- Http: timeout, 503 y circuito abierto -> errores tipados; no se filtra la key.
- Sin concurrencia/idempotencia (no mueve dinero ni persiste).
