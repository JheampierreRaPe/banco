## Objetivo

Cerrar el ciclo de una diferencia: el analista de operaciones abre un **reclamo** (`claims`) sobre
una excepcion, lo investiga y, si corresponde, lo resuelve con un **asiento de ajuste nuevo**
autorizado. El asiento original **nunca se edita ni se borra** (`docs/04#7.9`); el ajuste se
contabiliza por el motor y queda auditado.

## Alcance

- **Incluye:**
  - Migracion encadenada con `reconciliation.claims` (`docs/03b#12.2`): `exception_id FK`,
    `description`, `status`, `resolution`, `resolved_by`, `created_at`, `resolved_at`; `CHECK` de
    `status` (`OPEN`/`IN_REVIEW`/`RESOLVED`/`REJECTED`).
  - Servicio `create_claim`, `assign_claim`, `resolve_claim` (con o sin ajuste), idempotente por
    `Idempotency-Key` en la resolucion.
  - Endpoints (rol operaciones):
    - `POST /api/v1/reconciliation/exceptions/{id}/claims` -> `201` claim `OPEN`.
    - `POST /api/v1/reconciliation/claims/{id}/resolve` (Idempotency-Key obligatoria) body
      `{resolution, adjustment?}`; `adjustment` = `{amount_minor, currency, debit_account,
      credit_account, reason}` o `{amount_minor, currency, customer_account_id, direction}`.
  - **Asiento de ajuste:** si el ajuste afecta cuentas internas (`2200`/`6000`/`4100`/`1000`), se
    crea por `ledger.service.post_entry` con `entry_type=RECONCILIATION_ADJUSTMENT`. Si afecta una
    cuenta de cliente, se crea por la **fachada aditiva**
    `transactions.service.post_reconciliation_adjustment` (nueva, en este brief), que mueve el
    saldo por el `BalancePort` y registra el asiento por `ledger`; `reconciliation` no escribe
    `transactions`/`ledger` directamente.
  - Evento `claim.resolved` por `outbox` (payload `{claim_id, exception_id, status,
    adjustment_entry_id?, amount_minor, currency}` sin PII) + auditoria best-effort.
  - Actualizacion de la excepcion a `RESOLVED`/`DISMISSED` en la misma transaccion del claim.
- **No incluye:** UI (`E5-T21`), QA (`E5-T22`), edicion/borrado de asientos o transacciones,
  reversion automatica de la operacion original (si aplica, se hace con un ajuste nuevo).

## Contexto embebido (decisiones que aplican)

- **Regla de oro 2:** nunca se edita ni borra un asiento, transaccion o auditoria; se revierte con
  un asiento nuevo.
- **Asiento de ajuste (`docs/04#8` punto 5):** una diferencia confirmada se corrige con asiento de
  ajuste autorizado, nunca editando el original.
- **Partida doble (`docs/04#2`):** todo asiento debe cuadrar (`sum(debitos)=sum(creditos)`); el
  ajuste se registra por `ledger.service.post_entry`.
- **Frontera:** `reconciliation` es dueno de `claims`/`exceptions`; no escribe tablas de
  `transactions`/`ledger`. La fachada `post_reconciliation_adjustment` es **aditiva** y solo
  `transactions` la implementa.
- **Idempotencia:** la resolucion con ajuste exige `Idempotency-Key`; misma clave + mismo cuerpo =
  mismo claim/asiento; cuerpo distinto = `CONFLICT`.
- **Auditoria:** cada resolucion con ajuste deja rastro (`claim.resolved` + auditoria) con usuario,
  hora y antes/despues del estado del claim; sin PII.
- **Matriz de accesos:** solo el analista de operaciones; el ajuste requiere rol autorizado y queda
  auditado (`docs/13#2.3`).

## Modelo de datos

- `claims`: `id UUID PK`, `exception_id UUID FK`, `description TEXT NULL`, `status VARCHAR(15)`
  default `OPEN`, `resolution TEXT NULL`, `resolved_by UUID NULL`, `created_at`, `resolved_at NULL`.
- Indices: `(exception_id)`, `(status)`.
- No se agregan columnas a `transactions`/`ledger`; el asiento de ajuste usa
  `journal_entries.entry_type=RECONCILIATION_ADJUSTMENT` y `reference`/metadata para el claim.

## API / eventos

- **Endpoints:**
  - `POST /api/v1/reconciliation/exceptions/{id}/claims` -> `201`.
  - `POST /api/v1/reconciliation/claims/{id}/resolve` (`Idempotency-Key`) -> `200` con
    `{claim_id, status, exception_status, adjustment_entry_id?, replayed}`.
- **Eventos emitidos:** `claim.resolved` por `outbox`.
- **Eventos consumidos:** ninguno.
- **Errores de negocio:** `NOT_FOUND`, `NOT_AUTHORIZED`, `CONFLICT` (claim ya resuelto / idempotencia
  con cuerpo distinto), `VALIDATION_ERROR` (ajuste descuadrado o cuenta invalida).

## Reglas de negocio

- Un claim pertenece a una excepcion; no se puede abrir un claim sobre una excepcion ya `RESOLVED`.
- Resolver sin ajuste deja la excepcion `DISMISSED` o `RESOLVED` segun `resolution`; documentar.
- Resolver con ajuste crea **un** asiento nuevo cuadrado; nunca modifica el asiento original.
- El ajuste debe tener la misma moneda que la excepcion; si no, `VALIDATION_ERROR` (el FX es HU25).
- Si el ajuste toca una cuenta de cliente, el saldo se mueve por el motor; si no hay fondos
  suficientes en un debito, `REJECTED`/`INSUFFICIENT_FUNDS` sin asiento.
- Reintentar la resolucion con la misma `Idempotency-Key` devuelve el mismo claim/asiento
  (`replayed=true`); con cuerpo distinto -> `409 CONFLICT`.
- Sin PII en logs, evento ni auditoria.

## Criterios de aceptacion (CA)

- `CA-01` (HU19 CA-04): se puede abrir un claim sobre una excepcion y consultar su estado; solo el
  rol de operaciones.
- `CA-02`: resolver con ajuste crea **un asiento nuevo** cuadrado (`debitos=creditos`) y deja la
  excepcion/claim resueltos; el asiento original queda intacto.
- `CA-03`: idempotencia — misma clave/cuerpo no duplica asiento ni claim; cuerpo distinto -> `409`.
- `CA-04`: ajuste invalido (descuadrado, moneda distinta, cuenta inexistente) -> `422` sin asiento
  ni cambios de saldo.
- `CA-05`: se emite `claim.resolved` por `outbox` y se audita la accion (usuario, hora, antes/despues).
- `CA-06`: `pytest`/`ruff`/`black` y `alembic check` en verde.

## Pruebas requeridas

- Camino feliz: excepcion -> claim -> resolucion con ajuste interno -> asiento cuadrado; excepcion
  `RESOLVED`; evento y auditoria.
- Ajuste a cuenta de cliente: saldo sube/baja por el motor; asiento cuadrado; sin editar el original.
- Errores: ajuste descuadrado -> `422`; moneda distinta -> `422`; sin rol -> `403`; claim ya
  resuelto -> `409`.
- Idempotencia/concurrencia: dos resoluciones concurrentes con la misma clave -> un solo asiento;
  con claves distintas -> una gana y la otra `409`.
- Reverso: si el ajuste se revierte, se usa `ledger.reverse_entry`, no se borra.
