## Objetivo

Construir el **tablero del analista de fraude**: lista de alertas con severidad/estado, detalle con
evidencia, y acciones `RELEASE`/`BLOCK`/`DISMISS`. El panel solo muestra y envia; el backend decide
la alerta, el bloqueo y la auditoria.

## Alcance

- **Incluye:**
  - Feature `admin-web/src/features/fraud/`: `AlertsPage`, `AlertDetail`, chips de severidad/estado,
    filtros (estado, severidad, tipo, fecha) y paginacion.
  - Cliente API + hooks TanStack Query: `GET /risk/alerts`, `GET /risk/alerts/{id}`,
    `POST /risk/alerts/{id}/resolve`.
  - Detalle con `rule_code`, `type`, `severity`, `detail` acotado (IDs/montos/referencias, sin PII)
    y accion de resolucion con confirmacion.
  - Estados obligatorios: cargando, vacio, error, contenido (`docs/20#7`); mensajes en espanol.
  - Pruebas de componente/estados y de envio de acciones.
- **No incluye:** rutas/guards/menu global (los integra `F-T14`), backend (`E6-T01`..`E6-T04`),
  QA (`E6-T06`), edicion de reglas (el panel de reglas no es de este brief), datos sin enmascarar.

## Modelo de datos

Ninguno en el panel. Consume `risk.alerts` via API; no persiste nada localmente.

## API / eventos

- **Endpoints consumidos:**
  - `GET /api/v1/risk/alerts?status=&severity=&type=&user_id=&date_from=&date_to=&page=&page_size=`
  - `GET /api/v1/risk/alerts/{id}`
  - `POST /api/v1/risk/alerts/{id}/resolve` `{resolution, action}`
- **Eventos:** no consume eventos directamente.
- **Errores a mostrar:** `NOT_FOUND`, `NOT_AUTHORIZED`, `CONFLICT` (alerta ya resuelta),
  `VALIDATION_ERROR`.

## Reglas de negocio

- La severidad se muestra como chip (`LOW`/`MEDIUM`/`HIGH`/`CRITICAL`) con el color del design
  system; el estado (`OPEN`/`IN_REVIEW`/`RESOLVED`/`DISMISSED`) como badge.
- La accion de resolver exige confirmacion explicita; `BLOCK` advierte que mantiene el bloqueo.
- El panel no calcula el score ni la severidad; los muestra del servidor.
- No se muestran UUIDs crudos: se usa una referencia corta; cuentas/documentos enmascarados.
- Sin logica offline; error -> mensaje accionable + reintentar.

## Criterios de aceptacion (CA)

- `CA-01`: la pantalla lista alertas con filtros/paginacion y cubre los cuatro estados.
- `CA-02`: el detalle muestra regla, severidad, estado y evidencia acotada sin PII.
- `CA-03`: `RELEASE`/`BLOCK`/`DISMISS` envian la accion y reflejan el nuevo estado; `CONFLICT` se
  maneja con mensaje.
- `CA-04`: solo el rol de fraude accede (la guarda la integra `F-T14`; la feature no asume otro rol).
- `CA-05`: `npm test`/`tsc`/lint en verde; pruebas de estados e interaccion.

## Pruebas requeridas

- Componente: lista con datos/vacio/error/cargando; chips de severidad/estado.

- Seguridad: no se renderizan cuentas/documentos completos ni UUIDs crudos.
