## Objetivo

Versionar y actualizar las listas restrictivas **simuladas** sin reiniciar el servicio: cada lista
tiene `list_code`, `version` y `effective_from`; el oficial de cumplimiento puede consultar la
version vigente y recargar una version nueva, dejando auditoria. No persiste sujetos ni PII.

## Alcance

- **Incluye:**
  - Formato de archivo semilla versionado en `backend/app/adapters/data/sanctions/`
    (`ofac.v1.json`, `pep.v1.json`, `world_check.v1.json`) con entradas ficticias
    (`entity_id`, `name`, `aliases`, `document_number_hash` opcional, `country`, `type`).
  - Servicio `list_versions()` y `reload_lists(version_map)` que valida el manifiesto
    (`list_code`, `version`, `effective_from`, `checksum`) y deja la version vigente en
    `config.parameters` (`risk.sanctions_list_versions`, JSON) via `shared/config`.
  - Cache en proceso invalidable (o lectura por version) para que `E6-T07` use la version vigente;
    `reload` invalida la cache sin reiniciar.
  - Endpoints (rol `compliance_officer`/`admin`):
    - `GET /api/v1/compliance/lists` -> `200` con `list_code`, `version`, `effective_from`,
      `entries_count`, `checksum`.
    - `POST /api/v1/compliance/lists/reload` body `{list_code, version}` -> `200` con la version
      vigente; valida que el archivo exista y el checksum coincida; audita
      `compliance.lists.reloaded`.
  - Auditoria best-effort con usuario/hora/version anterior/nueva; sin PII.
- **No incluye:** tabla nueva de listas (D-S4-04: no esta en `docs/03b`), descarga real de OFAC/
  World-Check/PEP, cotejo (`E6-T09`), ROS (`E6-T10`), QA (`E6-T11`). No mueve dinero.

## Modelo de datos

No crea tablas. Usa `config.parameters` clave `risk.sanctions_list_versions` (JSON con
`{list_code: {version, effective_from, checksum}}`) y archivos JSON versionados.

## API / eventos

- **Endpoints:**
  - `GET /api/v1/compliance/lists`
  - `POST /api/v1/compliance/lists/reload`
- **Eventos:** ninguno de negocio; auditoria `compliance.lists.reloaded`.
- **Errores:** `NOT_FOUND` (lista/version inexistente), `NOT_AUTHORIZED`, `VALIDATION_ERROR`
  (checksum/manifiesto invalido).

## Reglas de negocio

- Una version es inmutable: recargar la misma version es idempotente; una version nueva reemplaza la
  vigente y conserva la anterior en el historial de `config.parameters`/auditoria.
- `effective_from` no puede ser futuro para activar (o se activa en la fecha; documentar).
- El checksum debe coincidir; si no, `VALIDATION_ERROR` y no se cambia la version vigente.
- El cotejo (`E6-T09`) usa siempre la version vigente; un `reload` se refleja sin reiniciar.
- Sin PII en logs/auditoria; solo `list_code`, `version`, checksum.

## Criterios de aceptacion (CA)

- `CA-01` (HU21 CA-04 base): `GET /compliance/lists` devuelve las listas con version vigente,
  `effective_from`, `entries_count` y `checksum`.
- `CA-02`: `POST /compliance/lists/reload` activa una version valida y se refleja en el cotejo sin
  reiniciar; una version invalida/checksum distinto -> `422` sin cambiar la vigente.
- `CA-03`: recargar la misma version es idempotente; queda auditoria con usuario/hora/version.
- `CA-04`: solo compliance/admin recarga; sin rol -> `403`; sin PII.
- `CA-05`: `pytest`/`ruff`/`black` en verde; `alembic check` limpio (sin migracion).

## Pruebas requeridas

- Camino feliz: listar versiones; recargar `v2`; el adaptador ve `v2`.
- Errores: version inexistente, checksum distinto, manifiesto invalido -> `404`/`422`.
- Idempotencia: misma version dos veces no duplica historial/efectos.
- RBAC: compliance/admin vs otro rol.
- Sin PII.
