## Objetivo

Dar al administrador de seguridad una vista para **consultar/editar parametros** (fachada existente
`GET/PUT /admin/parameters`) y **consultar/asignar roles** por `user_id` (`GET/POST
/admin/users/{id}/roles`, `docs/05#6.8`), con auditoria y datos enmascarados. El backend de roles se
agrega como fachada de `admin` sobre `identity`.

## Alcance

- **Incluye:**
  - **Corte 1 (backend):** fachada `identity.service.roles` (`get_user_roles`, `set_user_roles`) y
    endpoints `GET /api/v1/admin/users/{id}/roles` + `POST /api/v1/admin/users/{id}/roles`
    (`{roles: [...]}`) en `admin`, rol `security_admin`/`admin`; valida roles conocidos, audita
    `admin.roles.updated` (sin PII) y no toca `identity.users`/`roles` directamente (fachada).
  - **Corte 2 (panel):** feature `admin-web/src/features/admin/`:
    - `ParametersPage`: lista filtrable (`module`/`prefix`), edicion inline con validacion de tipo
      (enteros/decimales/JSON) y confirmacion; usa `GET/PUT /admin/parameters`.
    - `RolesPage`: input de `user_id` -> `GET /admin/users/{id}/roles`; asignar/revocar roles
      conocidos -> `POST`; muestra el resultado y la auditoria.
    - Estados obligatorios, mensajes en espanol, sin PII/tokens en logs.
  - Pruebas backend (roles) + panel (parametros/roles).
- **No incluye:** listado de usuarios internos (no hay endpoint; D-S4-06), alta/baja de usuarios,
  permisos finos por vista (la matriz es por rol), backend de parametros (`E2-T26`, `Hecho`),
  edicion de asientos.

  no escribe `config.parameters` directamente (fachada `shared/config`).

- **Panel (`docs/13#2.3`):** datos enmascarados, sesion separada, sin editar asientos.
- **Sin PII/tokens en logs.**
- **D-S4-06:** no hay endpoint de listado de usuarios internos; la vista pide `user_id` (UUID) y
  muestra una referencia corta. El listado queda como decision abierta.

## Modelo de datos

No crea tablas: usa `identity.roles`/`user_roles` (via fachada) y `config.parameters` (via
`shared/config`). No hay migracion nueva.

## API / eventos

- **Endpoints:**
  - `GET /api/v1/admin/parameters` / `PUT /api/v1/admin/parameters/{key}` (existentes).
  - `GET /api/v1/admin/users/{id}/roles` (nuevo, aditivo).
  - `POST /api/v1/admin/users/{id}/roles` (nuevo, aditivo) `{roles: [...]}`.
- **Eventos:** ninguno; auditoria `admin.roles.updated`/parametros.
- **Errores:** `NOT_FOUND` (usuario/clave), `NOT_AUTHORIZED`, `VALIDATION_ERROR` (rol/tipo).

## Reglas de negocio

- Solo roles conocidos (`operations_analyst`, `fraud_analyst`, `compliance_officer`,
  `credit_analyst`, `security_admin`, `auditor` + los existentes del sistema).
- Asignar roles es idempotente por usuario; revocar deja el rol fuera de `user_roles` (sin borrar
  historia si el modelo lo permite; documentar).
- Un cambio de parametro valida el tipo (entero/decimal/JSON) y se refleja sin reiniciar.
- No se puede dejar al ultimo `security_admin` sin rol (si aplica; decision abierta).
- Sin PII/tokens en logs.

## Criterios de aceptacion (CA)

- `CA-01`: `GET/PUT /admin/parameters` funciona desde el panel; tipos validados; auditoria.
- `CA-02`: `GET /admin/users/{id}/roles` devuelve los roles; `POST` asigna/revoca y audita.
- `CA-03`: solo `security_admin`/`admin`; sin rol -> `403`; usuario/clave inexistente -> `404`.
- `CA-04`: el panel cubre los cuatro estados; datos enmascarados; sin PII/tokens en logs.
- `CA-05`: `pytest`/`ruff`/`black` y `npm test`/`tsc` en verde; sin migracion.

## Regla de cliente delgado (dos campos)

El panel solo **consulta y envia**: muestra parametros/roles del servidor y envia el cambio; no
decide permisos, no calcula valores ni escribe `config.parameters`/`roles` por su cuenta. Sin logica
offline; el backend es la unica autoridad.
