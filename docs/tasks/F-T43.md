## Objetivo

Implementar en Flutter el flujo alterno de acceso **`/pin-reset`**: el usuario que recupera el acceso
pero no recuerda su PIN captura **email + DNI**, valida el **OTP `RECOVERY`** y fija un **PIN nuevo**
(crear + confirmar) contra `POST /api/v1/auth/pin-reset {email, doc_number, code, pin}`, terminando en
un paso **success**. El flujo **no abre sesion**: al exito solo navega a `/login?userRef=<user_ref>`
(la unica sesion la abre `POST /auth/login/pin`), con el diseno "Eucalipto y Ocre" y solo tokens y
componentes de `F-T34`.

## Contexto embebido (decisiones que aplican)

- **Decision del dueno (SCR-005 d3, `docs/18` §4):** extra backend = endpoint `/pin-reset`
  (**email + DNI + OTP**). El flujo de recuperacion tras SCR-005 es:
  `POST /auth/recovery/request` (email -> OTP `RECOVERY`) ->
  `POST /auth/recovery/verify` devuelve `{user_ref, device_bound}` (sin sesion) ->
  `POST /auth/pin-reset` fija el PIN -> `POST /auth/login/pin` abre la **unica** sesion.
- **Contrato `POST /api/v1/auth/pin-reset` (`docs/05` §6.1, E1-T34):** request
  `{email, doc_number, code, pin}` -> `data: {user_ref, pin_set: true}`; **no** abre sesion ni emite
  tokens; consume el OTP `RECOVERY` de `recovery.request`; el DNI se valida contra el hash HMAC
  server-side (nunca en claro). Errores: `401 INVALID_PIN_RESET` (**un unico** cuerpo generico para
  email no registrado, DNI que no coincide, sin OTP, codigo incorrecto, OTP vencido y OTP bloqueado:
  sin enumeracion ni oraculo de campo), `429 RATE_LIMITED` (ventana por `email+IP`), `422` estandar de
  FastAPI para email/PIN malformados o PIN debil (4-6 digitos).
- **OTP `RECOVERY` (`docs/05` §6.1, E1-T31):** `POST /auth/recovery/request {email}` responde
  **siempre 200** exista o no el email (`data: {accepted, ttl_seconds, resend_wait_seconds}`) y el
  reenvio reutiliza el `PENDING` vigente con cooldown; el OTP es **solo email** (sin SMS).
- **Sesion unica:** `/pin-reset` **no** abre sesion. Al exito se persiste best-effort el `user_ref`
  devuelto y se navega a `/login?userRef=<user_ref>`; nunca a `/home` ni se guardan tokens.
- **`SessionIdentityStore` (F-T20/F-T37):** guarda `user_ref` y es `Listenable`; aqui se usa para
  propagar la referencia al login (no para abrir sesion).
- **Diseno canonico (SCR-005 d1):** `pantallas.fig` (Eucalipto y Ocre) + tokens de `docs/20`. El
  mockup `pin-reset` (nodo `0:1062`) lo produjo `F-T42`; esta tarea lo consume.
- **Tokens/componentes de `F-T34`:** `AppColors`/`AppTypography`/`AppSpacing`/`AppRadii`/`AppShadows`,
  `AppPrimaryButton`/`AppSecondaryButton`/`AppGhostButton`, `AppTextField`, `AppCard`,
  `AppStatusChip`, `AppListItem`, y `LoadingView`/`EmptyView`/`ErrorView`. **No** introducir colores,
  fuentes ni radios nuevos.
- **Reuso de `F-T39`:** validadores y piezas del flujo PIN (`kPinLength`, `pinCreateError`,
  `pinConfirmError`, `isWeakPin`, `PinFlowHeader`, `PinStepHeading`, `PinCodeBoxes` y el teclado
  numerico) se importan en **solo lectura** desde `features/pin_setup`; no se modifican.
- **Estados obligatorios (`docs/20` §7):** cargando, vacio, error y contenido. Toda pantalla debe
  verse bien en los cuatro.
- **Reglas de banca (`docs/20` §8):** datos sensibles enmascarados, contraste accesible, objetivos
  tactiles >= 44px, mensajes claros y accionables.
- **Anti-enumeracion:** el copy y la navegacion son **identicos** exista o no el email; `401
  INVALID_PIN_RESET` cubre email/DNI/OTP con un unico mensaje; nunca indicar que campo fallo.
- **Datos sensibles:** el DNI, el OTP y el PIN **nunca** se loguean, no viajan en rutas/URL ni usan
  autofill/sugerencias; el DNI se muestra enmascarado. Sin PII en logs ni en mensajes.
- **Cliente delgado (`docs/19` §4):** la app solo captura y muestra; el backend valida email/DNI/OTP y
  fija el PIN. Sin logica offline.
- **Sin dependencias nuevas**; sin `pubspec.yaml`.

## Reglas de negocio

- Orden obligatorio del flujo: **email + DNI -> OTP -> nuevo PIN -> confirmar PIN -> success**.
- El OTP del flujo es el `RECOVERY` emitido por `recovery.request` (reenvio con cooldown
  `resend_wait_seconds` y cuenta atras `ttl_seconds`); OTP **solo email**.
- **`/pin-reset` no abre sesion:** al exito (`pin_set: true`) se persiste best-effort el `user_ref`
  devuelto y se navega a `/login?userRef=<user_ref>`; nunca se guardan tokens ni se navega a `/home`.
- **Anti-enumeracion:** mismo copy y misma navegacion exista o no el email; `401 INVALID_PIN_RESET`
  cubre email/DNI/OTP con **un unico** mensaje accionable; nunca revelar que campo fallo.
- **DNI:** se captura y se envia **solo** en el request final de `pin-reset`; se muestra enmascarado;
  nunca en logs, rutas ni mensajes.
- **PIN:** confirmacion local (coincidencia) como validacion de UI, no de negocio; el backend valida
  formato (4-6 digitos) y fija el PIN. PIN nunca en logs, rutas, autofill ni sugerencias.
- Cada pantalla cubre los **4 estados obligatorios** (cargando/vacio/error/contenido) con
  `LoadingView`/`EmptyView`/`ErrorView` y reintento accionable en error.
- La app **no** valida email/DNI/OTP ni decide si el reset procede: solo captura, envia y muestra.
- Sin logica offline; sin dependencias nuevas; sin PII en logs.
