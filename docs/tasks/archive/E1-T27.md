# E1-T27 - Registrar device_binding en el primer login exitoso con PIN

## Objetivo

Registrar el `device_binding` en el primer login exitoso con PIN: `POST /auth/login/pin` acepta `device_public_key` (`"hmac:<hex>"`), `platform` y `biometric_type`; si no existe binding para `(user, device)` lo registra (`register_binding`) y, si existe, actualiza `last_used_at` (`touch_binding`), de forma best-effort y auditada.

## Alcance

- **Incluye:**
  - Ampliar `PinLoginRequest` con `device_public_key`, `platform`, `biometric_type`.
  - En `login_with_pin`, tras exito del PIN: registrar o refrescar el binding del dispositivo.
  - Auditoria del registro/uso (fachada `audit`), best-effort.
- **No incluye:** un endpoint de enrolamiento aparte, cambios en el login facial/`nonce` (`E1-T13`), ni flujo de recuperacion (`E1-T19..T23`).

## Contexto embebido (decisiones que aplican)

- **Decision cerrada:** el binding biometrico se registra en el **primer login con PIN**; NO hay endpoint de enrolamiento aparte.
- **D07:** la biometria es local al dispositivo; el servidor solo valida el `nonce` firmado con la clave del `device_binding`.
- Formato de clave vigente (fallback documentado E1-T13): `public_key="hmac:<hex>"` (HMAC-SHA256); la ruta Ed25519/ECDSA queda lista si `cryptography` entra.
- `register_binding` (repo `bindings.py`) hace upsert de `(user_id, device_id)` y valida `platform in ("android","ios")` y `biometric_type in ("FACE","FINGERPRINT")`; `touch_binding` actualiza `last_used_at`.
- **Best-effort:** un fallo al persistir el binding NO debe romper el login (la sesion ya quedo creada); se loguea sin PII.
- Convencion: `flush` sin `commit`; el endpoint de PIN confirma en exito Y ante error de negocio (para que el contador persista).
- Nunca loguear `device_public_key` ni secretos.

## Modelo de datos

- `identity.device_bindings`: `user_id`, `device_id` (UQ con user), `public_key`, `platform`, `biometric_type`, `status='ACTIVE'`, `registered_at`, `last_used_at`.
- `identity.credentials`: contador/bloqueo del PIN (sin cambios).
- `identity.sessions`: sesion creada en el login (sin cambios).

## API / eventos

- **Endpoints:** `POST /auth/login/pin` (ampliado).
  - Request nuevo: `device_public_key` (opcional, `"hmac:<hex>"`), `platform` (`android|ios`), `biometric_type` (`FACE|FINGERPRINT`).
  - Response: sin cambios (`access_token`, `refresh_token`, `token_type`, `session_id`, `expires_in`).
- **Eventos emitidos:** `auth.login_succeeded` (sin cambios).
- **Eventos consumidos:** ninguno.
- **Errores de negocio:** se mantienen `INVALID_CREDENTIALS` (401), `ACCOUNT_LOCKED` (423); `platform`/`biometric_type` invalidos deben rechazarse/ignorarse sin romper el login (documentar la decision; no crear un oraculo 422-vs-401 sobre el PIN).

## Reglas de negocio

- El binding se registra SOLO tras un login con PIN exitoso (nunca en fallo/bloqueo).
- Si existe binding para `(user, device)` -> `touch_binding` (actualiza `last_used_at`, sin duplicar fila).
- Si no existe y llega `device_public_key` -> `register_binding` con `platform`/`biometric_type`.
- Si no llega `device_public_key` -> el login continua sin registrar (compatibilidad hacia atras).
- Un fallo al persistir el binding no revierte la sesion ni el token (best-effort) y se audita el intento.
- El `device_public_key` jamas se registra en logs.

## Criterios de aceptacion (CA)

- `CA-01` y `CA-02` de HU03 (login por biometria/PIN con dispositivo confiable).
- Base para `F-T22` (el cliente envia `device_public_key`).

## Pruebas requeridas

- Primer login PIN exitoso con `device_public_key` -> crea `device_bindings` (`status='ACTIVE'`, `last_used_at` coherente).
- Segundo login -> `touch_binding` (una sola fila, `last_used_at` actualizado).
- Login sin `device_public_key` -> no crea binding y el login funciona.
- Fallo al persistir el binding -> el login igual devuelve tokens (best-effort).
- `platform`/`biometric_type` invalidos -> no rompen el login (comportamiento documentado).
- El `device_public_key` no aparece en logs; auditoria registrada via fachada.
