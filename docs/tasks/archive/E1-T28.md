## Objetivo

Unificar la activacion y la creacion del PIN en un solo OTP: `setup_pin` valida el codigo `ACTIVATION` (`otp_service.validate_otp`) y, en la MISMA transaccion, fija `pin_hash` y transiciona `users.status: PENDING_ACTIVATION -> ACTIVE`, reutilizando la emision de `user.activated` ya existente en `validate_otp`; se elimina la exigencia de un segundo OTP en el alta.

## Alcance

- **Incluye:**
  - `setup_pin`: ademas de consumir el OTP y fijar el PIN, pasar el usuario a `ACTIVE` en la misma sesion.
  - `api/pin_setup.py`: ajustar el manejo transaccional si hace falta para que activacion + PIN + consumo del OTP sean atomicos.
- **No incluye:** tocar `otp_service` o `activation` (salvo import/consumo), cambiar la forma del request/response, ni el frontend (`F-T21`).

## Contexto embebido (decisiones que aplican)

- **Decision cerrada:** un solo OTP por email para activar + crear PIN (no dos codigos). SMS queda como fallback de entrega.
- `otp_service.validate_otp` consume el OTP (marca `USED`) y, SOLO con `purpose='ACTIVATION'`, enlista `user.activated` via `outbox` en la misma sesion. **No re-emitir el evento** en `setup_pin`.
- Comportamiento actual de `setup_pin` que se conserva: valida el formato del PIN (`4-6` digitos; `ValueError` -> 422) ANTES de consumir el OTP; `INVALID_SETUP_CODE` (401 generico, mismo cuerpo exista o no el usuario); `PIN_ALREADY_SET` (409); `flush` sin `commit`.
- El OTP valido ES la autorizacion (endpoint pre-sesion).
- **Prohibido loguear** PIN, codigo, hashes o PII.
- Con `EMAIL_PROVIDER=mock` (default) el codigo queda en `notifications.payload_json` para pruebas; el flujo es el mismo.

## Modelo de datos

- `identity.otp_codes`: `purpose='ACTIVATION'` consumido (estado `USED`).
- `identity.credentials.pin_hash`: fijado en la misma transaccion.
- `identity.users.status`: `PENDING_ACTIVATION -> ACTIVE`.

## API / eventos

- **Endpoints:** `POST /auth/pin/setup` (misma forma `{user_ref, code, pin}`; retorna `{user_id, status}` con `status='ACTIVE'`).
- **Eventos emitidos:** `user.activated` (lo enlista `validate_otp`; NO duplicar en `setup_pin`).
- **Eventos consumidos:** ninguno.
- **Errores de negocio:** se mantienen `INVALID_SETUP_CODE` (401), `PIN_ALREADY_SET` (409), `INVALID_PIN_FORMAT`/422.

## Reglas de negocio

- Al exito: el usuario queda `ACTIVE` y con `pin_hash` en la MISMA transaccion que consume el OTP (`flush`; el endpoint confirma).
- `validate_otp` sigue siendo la unica fuente de `user.activated`; no emitirlo de nuevo.
- Si el PIN ya existe -> `PIN_ALREADY_SET` (409) con el OTP valido ya consumido (se conserva la semantica actual: la validacion exitosa no se revierte).
- Codigo invalido/expirado/usado o usuario inexistente -> `INVALID_SETUP_CODE` generico (sin filtrar estado).
- PIN debil -> 422 antes de tocar el OTP.
- No exigir un segundo OTP en ningun punto del alta.

## Criterios de aceptacion (CA)

- `CA-02` de HU02 (validacion del OTP de 10 min al activar).
- `CA-04` de HU02 (acceso inicial habilitado al quedar `ACTIVE`).
- `CA-02` de HU03 (contingencia PIN operativa tras el alta).

## Pruebas requeridas

- Camino feliz: `setup_pin` con OTP `ACTIVATION` valido -> `pin_hash` fijado + `users.status='ACTIVE'` + `user.activated` enlistado UNA sola vez.
- Codigo invalido/expirado/usado -> 401 `INVALID_SETUP_CODE` (sin filtrar existencia) y sin cambios de estado.
- PIN ya fijado -> 409 `PIN_ALREADY_SET`.
- PIN debil -> 422 sin consumir el OTP.
- Atomicidad: un fallo posterior no deja al usuario `ACTIVE` sin PIN ni el OTP consumido a medias.
- El PIN/codigo no aparecen en logs ni respuestas.
