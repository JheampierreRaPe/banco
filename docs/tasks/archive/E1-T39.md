## Objetivo

Agregar `POST /auth/biometric/consent` (autenticado con JWT `Bearer`) que fija
`identity.credentials.biometric_enabled` (`{enabled: true|false}`) para el usuario del token, y
exponer `biometric_enabled` en la respuesta de `POST /auth/login/pin` para que el cliente sepa si el
boton biometrico aplica. Reutiliza la columna existente: **sin migracion**; `alembic check` queda
limpio.

## Reglas de negocio

- El consentimiento es por usuario: `POST /auth/biometric/consent` fija
  `credentials.biometric_enabled` del `user_id` del token. `enabled=false` revoca.
- El facial (`login_with_device`) sigue exigiendo `biometric_enabled is True`; sin el -> `400
  INVALID_LOGIN` generico. Habilitar -> el facial vuelve a ser posible (con binding `ACTIVE` + firma
  valida); revocar -> deja de serlo.
- El login con PIN devuelve el flag vigente **solo tras exito**; nunca altera el resultado del login
  (un fallo de lectura del flag no cambia el flujo; la credencial ya se obtuvo).
- `flush` sin `commit` en el servicio; el router confirma. `rollback` ante error inesperado.
- Sin PII/secretos en logs ni en respuestas; mensajes neutros. No se reflejan tokens, firmas ni
  `device_public_key`.
- Bindings `hmac:`/hashing intactos; no se toca `verify_signature` ni `hash_pin`.
- `alembic check` limpio (`previsto: no new upgrade operations detected`); `alembic current` sigue en
  `0020_identity_ruc_business_name (head)`.

## Criterios de aceptacion (CA)

- `CA-01`: `POST /auth/biometric/consent` con Bearer valido y `{"enabled": true}` deja
  `credentials.biometric_enabled = true`; con `{"enabled": false}` lo revoca; ambas idempotentes.
- `CA-02`: sin cabecera/`Bearer` invalido o `sub` no UUID -> `401 NOT_AUTHENTICATED`; credencial
  inexistente -> `404 NOT_FOUND` neutro; el cuerpo no filtra datos.
- `CA-03`: `POST /auth/login/pin` responde `data.biometric_enabled` con el valor real (`true`/`false`)
  sin alterar tokens, `session_id`, `expires_in` ni errores.
- `CA-04` (regresion facial): habilitar el consentimiento -> `login_with_device` con nonce/firma
  validos y binding `ACTIVE` abre sesion; revocar -> `400 INVALID_LOGIN` generico (mismo cuerpo que
  hoy, sin sesion).
- `CA-05`: sin migracion (`alembic check` limpio); `docs/05#6.1`, `docs/modules/README.md`
  (`identity`) e `identity/README.md` actualizados; `pytest`/`ruff`/`black` verdes, sin borrar
