## Objetivo

Insertar el reto biometrico del dispositivo dentro del flujo de pago en Flutter: cuando el backend
devuelve `PENDING_AUTHORIZATION`, la app pide la biometria del SO, firma el `nonce` con la clave en
almacenamiento seguro y llama a `POST /transactions/{id}/authorize`, continuando o mostrando el
fallo.

## Alcance

- **Incluye:** UI del reto (bottom sheet/pantalla), reutilizacion del `BiometricReader` y del
  firmador de `nonce` de `features/biometrics`, manejo de fallo/fallback a PIN (borde), estados de
  UI y accesibilidad, integracion en el flujo de transferencia (`E2-T11`).
- **No incluye:** el backend de autorizacion (`E2-T17`/`E2-T19`), el cambio de umbral (`E2-T18`),
  la notificacion (`E2-T20`), otros features.

## Contexto embebido (decisiones que aplican)

- La validacion no debe anadir `> 3 s`: UI fluida, sin bloqueos de hilo (`docs/07#hu08...`).

## Modelo de datos

Sin persistencia de biometricos/frames. Estado efimero: `transaction_id`, `nonce`, estado de reto.
La clave de firma vive en almacenamiento seguro (`flutter_secure_storage`).

## API / eventos

- **Endpoints consumidos:** `POST /transactions/{id}/authorize` (`Idempotency-Key`),
  `GET /transactions/{id}`. Puede consumir un challenge de `nonce` si `E2-T17` lo expone.
- **Eventos:** ninguno (cliente).
- **Errores a mapear:** `PENDING_AUTHORIZATION` (dispara reto), `EXPIRED_NONCE`,
  `NOT_AUTHORIZED` (firma/binding), `CONFLICT`, `INSUFFICIENT_FUNDS`.

## Reglas de negocio

- El reto se dispara solo si el backend indica `PENDING_AUTHORIZATION`; la app no decide umbrales.
- Firma valida -> continuar el flujo (confirmacion/comprobante); fallo -> mensaje claro, opcion de
  reintentar o usar PIN como fallback, sin revelar el motivo exacto.
- Si el dispositivo no tiene biometria disponible, ofrecer el fallback (PIN) segun el flujo vigente.
- Reutilizar la misma `Idempotency-Key` al reintentar.

## Criterios de aceptacion (CA)

- `CA-01` de HU08 (UI): el pago sobre el umbral exige el reto biometrico y no continua sin exito.
- `CA-02` (UI, parcial): el fallo se comunica y registra el intento (via backend).
- La interaccion se siente inmediata (`<= 3 s` percibido).

## Pruebas requeridas

- Camino feliz: pago sobre umbral -> reto -> firma exitosa -> continuacion del flujo.
- Errores: biometria cancelada/fallida -> fallback PIN/mensaje; `EXPIRED_NONCE` -> reintento;
  sin disponibilidad biometrica -> fallback.
- Idempotencia: reintento reutiliza la misma `Idempotency-Key` (prueba del controlador/servicio).
