## Objetivo

Exponer `POST /api/v1/transactions/{id}/reverse` para compensar una operacion con un **asiento
inverso** (nunca editando ni borrando el original), idempotente y **solo** para los estados
permitidos, dejando la operacion original intacta y trazada. Es el reverso autorizado del catalogo
de operaciones (`docs/05#6.3`).

## Alcance

- **Incluye:** endpoint, esquema de request (`reason` opcional), validacion de estado permitido,
  RBAC/propiedad, `Idempotency-Key`, asiento inverso via `ledger.service.reverse_entry` con
  referencia `reverses_journal_entry_id`, transicion de estado (`REVERSED`), evento por `outbox`,
  contrato OpenAPI.
- **No incluye:** el reverso automatico de la saga interbancaria (`E2-T09`; se mantiene igual), la
  conciliacion (`reconciliation`, Sprint 4), el comprobante (`E2-T10`), la UI (fuera de lote).

## Contexto embebido (decisiones que aplican)

- El ledger es **append-only**: no se edita ni se borra; se corrige con un asiento nuevo
  (`docs/04#2`, `docs/04#11`, `docs/04#9`). Un cambio de dinero **nunca** edita asientos
  (`docs/18#3`).
- El reverso invierte los movimientos del asiento original con
  `reverses_journal_entry_id`; el original permanece (`docs/04#9`, `docs/04#3`).
- Idempotencia obligatoria (endpoint de dinero): misma `Idempotency-Key` + mismo cuerpo = mismo
  resultado; cuerpo distinto -> `409` (`docs/04#5`, `docs/05#3`).
- Solo el motor cambia de estado; cada cambio deja fila en `transaction_status_history`
  (`docs/04#3`).
- Sin logica en el router: valida, traduce y delega al `service/` (`docs/05#1`); respuesta
  `{"data", "meta"}` (`docs/05#4`). Idempotencia y validacion las aplica el servidor
  (`docs/19#4-cliente-delgado-estricto`).
- **Estados permitidos (supuesto G17):** `SETTLED`, `POSTED`, `CONCILIATED` pueden reversarse;
  `INITIATED`/`VALIDATED`/`PENDING_AUTHORIZATION`/`AUTHORIZED`/`FUNDS_HELD` no (usar
  cancelacion/liberacion de hold, no reverso); `REJECTED`/`FAILED`/`REVERSED` son terminales y
  no se reversan. Se registra en `docs/18` §9 lo que se fije.

## Modelo de datos

Lee/actualiza `transactions.status`/`version` y `transaction_status_history`
(`docs/03b#61`, `#62`). El asiento inverso vive en `ledger` (`journal_entries.reverses_entry_id`,
`docs/03b#7.2`) creado por la fachada. No crea tablas.

## API / eventos

- **Endpoint:** `POST /api/v1/transactions/{id}/reverse` -> `200 {data: {transaction_id, status,
  reversal_entry_id, reverses_entry_id}}`. `Idempotency-Key` obligatoria. Request opcional:
  `{reason?: str}`.
- **Eventos emitidos:** `transfer.reversed` o `transaction.reversed` (nombre a fijar; registrar en
  `docs/18` §9), via `outbox`; y el `ledger.entry.posted` del asiento inverso (lo emite `ledger`,
  `E2-T23`).
- **Eventos consumidos:** ninguno obligatorio.
- **Errores de negocio:** `NOT_FOUND` (transaccion inexistente), `NOT_AUTHORIZED` (no es el
  titular / sin rol de operaciones, generico), `CONFLICT` (estado no permitido para reverso;
  idempotencia con cuerpo distinto), `VALIDATION_ERROR` (payload malformado).

## Reglas de negocio

- Solo se reversa en los estados permitidos; en otro estado -> `409` (no `REVERSED`).
- El reverso crea un **asiento inverso** (debe/haber invertidos) que referencia el original
  (`reverses_entry_id`); el original **nunca** se marca borrado ni se edita.
- Cuadre: el asiento inverso cumple `sum(debitos)=sum(creditos)` por moneda; la suma del original
  + inverso es cero por cuenta.
- Idempotente: doble llamada con la misma `Idempotency-Key` no crea dos asientos inversos ni
  re-reversa; devuelve el mismo resultado.
- La operacion original pasa a `REVERSED` (terminal) con fila en `transaction_status_history`.
- No mueve dinero fuera del ledger; sin `float`; sin PII en logs.

## Criterios de aceptacion (CA)

- `CA-01`: un reverso de una transaccion `SETTLED`/`POSTED`/`CONCILIATED` genera asiento inverso
  cuadrado y deja el original intacto (`REVERSED`).
- `CA-02`: estado no permitido -> `409`, sin crear asiento.
- `CA-03`: idempotencia: doble llamada no duplica el asiento inverso.
- `CA-04`: el asiento inverso referencia el original (`reverses_entry_id`) y ambos permanecen.

## Pruebas requeridas

- Camino feliz: transferencia `SETTLED` -> reverso -> asiento inverso cuadrado; saldos vuelven al
  estado previo; el original sigue `POSTED`/`SETTLED` en el ledger y la transaccion pasa a
  `REVERSED`.
- Errores: transaccion inexistente -> `404`; estado no permitido -> `409`; ajena -> `403`;
  `Idempotency-Key` con cuerpo distinto -> `409`.
- Concurrencia/idempotencia: dos `reverse` concurrentes con la misma clave -> un solo asiento
  inverso; concurrencia sin doble compensacion.
