## Objetivo

Reconstruir el `entry_type` de las filas **historicas** de `accounts.movements_view` que la
migracion `0027_movements_entry_type` dejo en `NULL`, tomando el valor desde la **fuente de verdad**
(`ledger.journal_entries.entry_type`), de forma **idempotente y reproducible**, para que el frontend
deje de pintar esas filas como "Movimiento" generico y no duplique patas internas historicas.

## Alcance

- **Incluye:**
  - Migracion de datos nueva `0028_backfill_entry_type` (`down_revision = "0027_movements_entry_type"`)
    que resuelve `movements_view.entry_type` por fila haciendo join por
    `movements_view.journal_entry_id = journal_entries.id` y copiando
    `journal_entries.entry_type`; solo sobre filas con `entry_type IS NULL`.
  - Manejo de filas huerfanas/no resolubles (sin `journal_entries` asociado, o con `entry_type`
    vacio defensivo): quedan `NULL` con el **fallback ya existente del cliente** ("Movimiento"),
    sin borrar ni marcar filas.
  - `downgrade()` documentado (revierte solo el dato, no el esquema).
  - Pruebas (pobla filas existentes; idempotencia; no resolubles; no sobrescribe filas ya pobladas;
    ciclo de migracion).
  - Docs: `docs/03b#5.4`, `docs/modules/README.md#accounts`, `docs/18#9` (gap nuevo) e indice
    `docs/tasks/SPRINT-2.md`.
- **No incluye:** el motor de dinero (`ledger.service`, asientos, postings, cuadre, reverso); el
  payload de `ledger.entry.posted` ni la proyeccion en runtime (`accounts/repository/movements.py`,
  `accounts/events`); el contrato de `GET /accounts/{id}/movements` (ya expone `entry_type` desde
  E2-T35); ningun cambio al frontend (el fallback `NULL -> "Movimiento"` ya existe); `identity`/
  `risk`/`notifications`/`credits`/`wallet`/`fx`; `shared/config`.

## Contexto embebido (decisiones que aplican)

- **Sintoma (observacion MEDIA del validador, 2026-10-09):** la migracion `0027_movements_entry_type`
  agrego la columna `accounts.movements_view.entry_type` (`VARCHAR(30)`, nullable) **sin backfill**;
  las filas ya proyectadas quedaron `entry_type = NULL`, el frontend las pinta como "Movimiento" y
  puede mostrar patas internas historicas (`hold`/`settle`) duplicadas.
- **Decision del dueno (autoritativa):** **reconstruir/backfill** las filas historicas desde la
  fuente de verdad (`ledger.journal_entries.entry_type`), de forma **idempotente y reproducible**.
- **Fuente de verdad:** `ledger.journal_entries.entry_type` (`String(30)`, `nullable=False`;
  `backend/app/modules/ledger/models/__init__.py:87`; definida en `docs/03b#7.2-journal_entries`).
  `movements_view.journal_entry_id` es una **REF logica** al `id` del asiento (sin FK fisica entre
  schemas; `accounts/repository/movements.py:74,93`) y ya contiene el `entry_id` del evento.
- **Mecanismo elegido — migracion de datos `0028_*` (no `rebuild_entry_movements`):**
  - `rebuild_entry_movements` (`accounts/repository/movements.py:330-361`) **borra y re-deriva** las
    filas desde los `postings` que **entrega el evento/fachada**, que **no estan persistidos** en
    `accounts`; ademas re-aplica la regla de atribucion y puede cambiar el conjunto de filas
    (p. ej. omitir patas de sistema). No es un backfill puro de una columna y es mas riesgoso.
  - La migracion `0028` es el item **minimo, acotado y seguro**: copia una columna por `join`, sin
    tocar el conjunto de filas, sin mover dinero y sin re-ejecutar la proyeccion.
- **Regla de oro 4 vs migracion de datos:** un modulo **no** accede a tablas de otro en runtime
  (`docs/16#2` regla 4). La migracion es **capa de datos/esquema** (corre con Alembic, no con
  imports de la app) y **solo lee** `ledger.journal_entries`; **no** importa modelos de `ledger`, **no**
  escribe en `ledger` y no cambia el motor de dinero. Esta excepcion queda **explicitamente
  autorizada** por este brief y documentada en la migracion.
- **Idempotencia/reproducibilidad:** el `UPDATE` filtra `WHERE entry_type IS NULL` (re-ejecutable sin
  cambios); misma base -> mismo resultado; reversible con el `downgrade`.
- **Filas no resolubles:** `movements_view.journal_entry_id` sin fila en `journal_entries`, o con
  `entry_type` nulo/vacio (defensivo): se **dejan `NULL`** (no se borran ni marcan); el cliente ya
  aplica fallback ("Movimiento") sin mostrar texto crudo (`E2-T35`,
  `frontend/lib/features/accounts/models/movement_concept.dart`).
- **Limite de `alembic_version.version_num`:** `VARCHAR(32)` (ver `E2-T33`/`0027`); el nombre de
  revision debe ser <= 32 chars (`0028_backfill_entry_type` = 24).
- **No borrar pruebas para pasar**; documentar lo que se adapta (`docs/tasks/SPRINT-2.md`).

## Modelo de datos

- Tabla `accounts.movements_view` (`docs/03b#5.4`): se **puebla** la columna existente
  `entry_type VARCHAR(30)` (nullable) de las filas historicas; sin cambio de tipo ni de columnas.
- Fuente: `ledger.journal_entries.entry_type` (`docs/03b#7.2`; `String(30) NOT NULL`).
- Migracion nueva `0028_backfill_entry_type` (`down_revision = "0027_movements_entry_type"`):
  - `upgrade()` / `backfill_data(bind)`:
    ```sql
    UPDATE accounts.movements_view AS mv
       SET entry_type = je.entry_type
      FROM ledger.journal_entries AS je
     WHERE mv.journal_entry_id = je.id
       AND mv.entry_type IS NULL
       AND je.entry_type IS NOT NULL;
    ```
    (sintaxis Postgres; para SQLite de pruebas usar `UPDATE ... WHERE journal_entry_id IN (SELECT
    id FROM ledger.journal_entries ...)`, o el patron portable equivalente; documentar la variante
    segun el `bind.dialect.name`). Idempotente por el filtro `IS NULL`.
  - `downgrade()`: `UPDATE accounts.movements_view SET entry_type = NULL` (inverso documentado:
    deja la columna en el estado inmediatamente posterior a `0027`; el esquema no cambia y el
    `upgrade` re-ejecutable repuebla; `0027.downgrade()` es quien retira la columna).
  - Ciclo CI: `alembic upgrade head` + `downgrade -1` + `upgrade head` en base limpia
    (`docs/15#4`) + `alembic check` limpio.

## Reglas de negocio

- `entry_type` por fila = `ledger.journal_entries.entry_type` del asiento referenciado por
  `movements_view.journal_entry_id` (mismo valor para las patas de un asiento).
- Solo se actualizan filas con `entry_type IS NULL`; las ya pobladas (por la proyeccion E2-T35) **no**
  se sobrescriben.
- Filas huerfanas o no resolubles: se **dejan `NULL`** (fallback del cliente), sin borrar/marcar.
- El backfill es **read-only** sobre `ledger` (no crea asientos, no altera `postings`/cuadre).
- **No** se re-ejecuta la proyeccion (`rebuild_entry_movements`) ni cambia el conjunto de filas.

## Criterios de aceptacion (CA)

- `CA-01` (backfill): tras `0028`, las filas historicas con asiento resoluble tienen
  `entry_type` = `journal_entries.entry_type`; las que ya lo tenian **no** cambian.
- `CA-02` (idempotencia): re-ejecutar el `upgrade`/backfill no altera valores ni duplica nada;
  `alembic upgrade head` repetido es no-op.
- `CA-03` (no resolubles): una fila cuyo `journal_entry_id` no existe en `journal_entries` permanece
  `NULL` sin error; el cliente la resuelve con fallback.
- `CA-04` (reversible): `upgrade head` -> `downgrade -1` -> `upgrade head` verdes y
  `alembic check` limpio.
- `CA-05` (sin tocar el motor): no hay escrituras a `ledger.*`, no cambian `postings`/asientos/cuadre,
  y no cambia el payload de `ledger.entry.posted` ni la proyeccion en runtime.
- `CA-06` (doc): `docs/03b#5.4` y `docs/modules/README.md#accounts` dejan de decir "sin backfill";
  `docs/18#9` registra el gap nuevo; indice en `docs/tasks/SPRINT-2.md`.
