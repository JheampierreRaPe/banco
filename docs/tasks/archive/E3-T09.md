## Objetivo

Construir el flujo Flutter de **solicitud de credito**: formulario de datos, **consentimiento
explicito** para consulta en centrales de riesgo y pantalla de **estado del expediente**
(incluyendo `EN_REVISION`), presentando solo lo que responde el backend.

## Alcance

- **Incluye:** pantallas en `frontend/lib/features/credits/` (`presentation/`), servicio sobre
  `ApiClient` para `POST /credits/applications` (con `Idempotency-Key`) y
  `GET /credits/applications/{id}`; checkbox de consentimiento obligatorio; validacion de UX;
  pantalla de estado con los estados del enum; los 4 estados de UI.
- **No incluye:** simulador (`E3-T04`), panel del analista (`E3-T10`), backend
  (`E3-T06`..`E3-T08`).

## Contexto embebido (decisiones que aplican)

- **Cliente delgado estricto:** el dispositivo no decide la elegibilidad ni calcula DTI/score;
  solo envia datos y **muestra el dictamen del servidor** (`docs/19#1-principio`,
  `docs/13#12-reglas-de-frontend`).
- **Consentimiento explicito obligatorio** antes de enviar: sin marcar el checkbox, el boton de
  envio queda bloqueado; la validacion autoritativa es del backend (`docs/08#hu10...`).
- `POST /credits/applications` **crea recurso** -> usar `ApiClient.postWithIdempotency`; un
  reintento reutiliza la misma clave (`frontend/lib/features/README.md` regla 4).
- Feature NUNCA toca `app_router.dart`; expone/actualiza `credits_routes.dart`.
- Pantallas usan `LoadingView`/`EmptyView`/`ErrorView`; 4 estados obligatorios; tokens `docs/20`.
- Datos sensibles enmascarados; sin API keys embebidas; sin PII en disco (`docs/13#12...`).

## Modelo de datos

Sin persistencia local de dinero. Modelos Dart: `LoanApplicationRequest`, `LoanApplicationStatus`
(espejo del enum: `DRAFT`, `SUBMITTED`, `IN_EVALUATION`, `APPROVED`, `REJECTED`, `IN_REVIEW`,
`EXPIRED`), `LoanApplicationResult` (id, estado, dictamen, motivo, montos). No guardar PII en disco.

## API / eventos

- **Endpoints consumidos:**
  - `POST /credits/applications` (`Idempotency-Key`, incluye el flag/estado de consentimiento).
  - `GET /credits/applications/{id}` (estado; refresco/polling opcional).
- **Eventos emitidos/consumidos:** ninguno.
- **Errores de negocio a mapear:** `VALIDATION_ERROR` (campos/consentimiento), `NOT_FOUND`,
  `CONFLICT`, `BUREAU_UNAVAILABLE` (mostrar `EN_REVISION`, no error).

## Reglas de negocio

- El formulario no permite enviar sin consentimiento marcado.
- La UI no interpreta el dictamen: muestra exactamente `APROBADO`/`RECHAZADO`/`EN_REVISION` con el
  `decision_reason` del backend.
- `EN_REVISION` se comunica como "en evaluacion manual", sin prometer aprobacion.
- Reintentos de red reutilizan la misma `Idempotency-Key` del intento en curso.
- Montos formateados; sin exponer PII.

## Criterios de aceptacion (CA)

- `CA-01` de HU10 (autorizacion bureau): la app exige el consentimiento antes de enviar.
- `CA-02` de HU10 (validacion de campos): faltantes se senalan antes de enviar (UX) y el backend
  manda.
- `CA-04` de HU10 (estado visible): pantalla de estado del expediente con `EN_REVISION` soportado.
- 4 estados de UI y errores en espanol accionables.

## Pruebas requeridas

- Camino feliz: formulario -> consentimiento -> envio -> estado `APROBADO`/`EN_REVISION` (servicio
  mockeado).
- Errores: sin consentimiento -> no se envia; `422`/`404`/`409`/`BUREAU_UNAVAILABLE` mapeados.
- Idempotencia: un reintento reutiliza la misma `Idempotency-Key`.
- Estados vacio/carga/error.
