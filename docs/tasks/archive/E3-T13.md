# E3-T13 - Servicio de firma: hash del documento + token biometrico del dispositivo + sello

## Objetivo

Implementar el servicio de firma del contrato con **no repudio**: emitir/consumir un `nonce` de un
solo uso ligado al contrato, verificar la **firma biometrica del dispositivo** contra el
`device_binding` vigente (fachada `identity`, D-03), **sellar** el documento (`doc_hash` +
`signed_at` + `signature_token_hash`) y persistir el hash del token biometrico sin permitir su
**reutilizacion**. No mueve dinero.

## Alcance

- **Incluye:** `domain/signing.py` (sello puro y determinista), `service/signing.py`
  (`request_signature_challenge` + `sign_contract`), consumo del `nonce` de un solo uso, verificacion
  de la firma por **fachada** `identity` (D-03: `device_login.verify_signature` +
  `device_login.get_device_binding`), persistencia `contracts.signature_token_hash`/`signed_at`/
  `status=SIGNED`, regla de **no reutilizacion** del token, evento `credit.contract.signed` por
  `outbox` y auditoria best-effort.
- **No incluye:** los endpoints HTTP y el envio de copia por correo (`E3-T14`), la generacion de los
  documentos (`E3-T12`), la UI (`E3-T15`), la QA (`E3-T16`). No expone router propio.

## Contexto embebido (decisiones que aplican)

- **Biometria del dispositivo (no liveness):** HU11 firma con biometria del dispositivo; el
  `nonce` lo firma la clave del `device_binding` tras el desbloqueo local (`docs/01#2-contradicciones-detectadas-y-resolucion`,
  contradiccion 8; `docs/02-arquitectura.md#10-seguridad-arquitectonica`). El liveness del KYC es
  solo de HU01.
- **Mecanismo existente reutilizable:** `identity.domain.nonce` (`issue_nonce`/`consume_nonce`,
  un solo uso, TTL 120 s) y `identity.service.device_login` (`verify_signature`,
  `get_device_binding`) ya existen (E1-T13/E2-T17, D-03). La firma se verifica contra la clave
  vigente del binding; cualquier desajuste responde **generico, sin oraculo**.
- **Token biometrico cifrado y no reutilizable** (`docs/08#hu11---firma-digital-de-contrato-con-biometria-facial-must-8-sp-sprint-3`):
  se guarda **el hash** del token (`signature_token_hash`, `docs/03b#86-contracts`), nunca el
  material en claro; el `nonce` es de un solo uso y el token no se acepta dos veces.
- **Prohibido guardar frames/biometricos ni secretos**; solo el resultado; **sin PII en logs**
  (`docs/02#10`, `docs/16-guia-para-agentes.md#2-reglas-de-oro-no-negociables`, reglas 7 y 10).
- **Fronteras por fachada/evento:** `credits` consume `identity` por `service/` (sin importar sus
  modelos, `docs/02#52`); publica por `outbox` (regla 8).
- **HU11 no mueve dinero:** no se crea `loans`/asientos; el desembolso es HU12.
- **Alembic:** si se agregara una columna nueva (sello explicito), migracion encadenada tras `0033`
  y `alembic check` limpio; por defecto este brief **no** agrega columnas (ver Decisiones abiertas).

## Modelo de datos

Lee/actualiza `credits.contracts` (`docs/03b#86-contracts`): `doc_hash` (entrada), `status`
(`GENERATED` -> `SIGNED`), `signed_at` (estampa el servidor), `signature_token_hash` (hash del token

se lee por fachada, no se copia.

## API / eventos

- **Endpoints:** ninguno propio; habilita el flujo que consumira `POST /credits/applications/{id}/sign`
  (`E3-T14`). Puede exponer la funcion de servicio para emitir el reto (que `E3-T14` publica como
  endpoint `.../sign/challenge`, ver Decisiones abiertas).
- **Eventos emitidos (via `outbox`; registrar en `app/core/events.py` y `docs/18`):**
  `credit.contract.signed` (payload sin PII: `contract_id`, `application_id`, `user_id`, `status`).
- **Eventos consumidos:** ninguno obligatorio.
- **Errores de negocio:** `NOT_AUTHORIZED` (firma/binding invalido, **generico** sin oraculo),
  `EXPIRED_NONCE` (`nonce` vencido o reutilizado), `CONFLICT` (contrato no `GENERATED` o ya
  `SIGNED`), `NOT_FOUND` (contrato inexistente/ajeno, neutro).

## Reglas de negocio

- Solo un contrato **`GENERATED`** del titular se firma; en otro estado -> `CONFLICT`. Un contrato
  ya `SIGNED` no se vuelve a firmar.
- El `nonce` es de **un solo uso** con TTL corto (reutilizarlo -> `EXPIRED_NONCE`/generico).
- La firma se valida contra el `device_binding` **vigente** (`status=ACTIVE`) del usuario por la
  fachada de `identity`; cualquier desajuste responde **generico** (`NOT_AUTHORIZED`), sin filtrar
  motivo ni existencia.
- **No reutilizacion del token:** `signature_token_hash` = hash (SHA-256) del token biometrico
  (firma + `nonce` + `device_id` + `contract_id`); reutilizar el mismo token en otro contrato/firma
  se rechaza (unicidad/verificacion). El token en claro **nunca** se persiste ni se loguea.
- **Sello (no repudio):** el sello combina `doc_hash` + `signed_at` + `signature_token_hash` de
  forma determinista (`domain/signing.py`), reproducible para verificar integridad; guardarlo o no
  como columna propia es una decision abierta.
- Registrar el instante del servidor en `signed_at` (no se acepta del cliente).
- No mueve dinero; sin asientos; sin `loans`.
- Sin PII/secretos en logs; solo IDs/estado.

## Criterios de aceptacion (CA)

- `CA-02` de HU11 (consentimiento biometrico): la firma exige una firma valida del dispositivo
  (no hay firma si el `nonce`/binding es invalido).
- `CA-03` de HU11 (firma certificada): el contrato pasa a `SIGNED` con `signed_at` + `doc_hash` +
  `signature_token_hash` (sello), persistido para no repudio.
- No reutilizacion: el `nonce` de un solo uso y el token no se pueden reusar; la segunda firma
  falla sin cambiar el contrato.
- Aislamiento: firmar no crea `loans`/asientos ni mueve dinero.

## Pruebas requeridas

- Camino feliz: contrato `GENERATED` + `nonce` valido + firma valida -> `status=SIGNED`,
  `signed_at` + `signature_token_hash` persistidos; evento `credit.contract.signed`.
- Errores: firma/binding invalido -> rechazo **generico** sin cambiar el contrato; `nonce` vencido;
  `nonce` reutilizado; contrato ya `SIGNED` -> `CONFLICT`; contrato ajeno -> `NOT_FOUND`.
- No reutilizacion: reutilizar el token/firma -> rechazo; dos firmas -> un solo `SIGNED`.
- Fachada (D-03): la verificacion usa `identity.service.device_login.verify_signature` +
  `get_device_binding` (prueba unitaria de la frontera sin importar modelos de `identity`).
- Sin PII/secretos en logs.

## Decisiones abiertas (requieren al dueno)

1. **Sello explicito vs derivado.** `docs/03b#86` no tiene columna de sello: el sello puede ser la
   combinacion determinista `doc_hash` + `signed_at` + `signature_token_hash` (recomendado, sin
   migracion) o una columna nueva `seal_hash` (migracion `0034`). Confirmar.
2. **Cifrado del token.** La HU dice "se guarda cifrado" y `03b` dice `signature_token_hash`
   (hash). Se adopta **hash** (irreversible) por defecto; si el dueno quiere poder recuperar el
   token, habria que cifrarlo (AES-256-GCM, patron `beneficiaries_crypto`) y cambiar el esquema.
3. **Reto de firma del contrato.** Reutilizar `identity.domain.nonce` con un endpoint de reto
   propio (`.../sign/challenge`, analogo a `POST /transactions/{id}/authorize/challenge`) o un
   `nonce` ligado al contrato; definir en `E3-T14` y documentar el gap de la ruta.
4. **Emisor del `nonce`:** `identity` (reuso puro) vs un emisor propio de `credits`; se recomienda
   reutilizar `identity.domain.nonce` (sin persistir, un solo uso) para no duplicar el mecanismo.
