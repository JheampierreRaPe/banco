## Objetivo

Construir el flujo Flutter de **cronograma definitivo del prestamo** y **activacion/desactivacion
del debito automatico** (y el pago manual de una cuota), mostrando los datos que devuelve el backend
(montos, fechas, estado por cuota, saldo de capital) y cubriendo los 4 estados de UI, sin calcular
ni decidir nada en el cliente.

## Alcance

- **Incluye:** pantallas en `frontend/lib/features/credits/presentation/` para:
  (1) listar los prestamos del titular (`GET /credits/loans`) y (2) ver el **cronograma definitivo**
  (`GET /credits/loans/{id}/schedule`) con filas por cuota (N, vencimiento, capital, interes, seguro,
  total, estado `Pendiente`/`Parcial`/`Pagada`/`Vencida`);
  (3) toggle de **debito automatico** (`PUT /credits/loans/{id}/auto-debit`);
  (4) **pagar** una cuota pendiente (`POST /credits/loans/{id}/pay`, con `ApiClient.postWithIdempotency`).
  Servicio Dart sobre `ApiClient`, modelos de respuesta, 4 estados de UI (contenido/carga/vacio/error
  con Reintentar), mensajes en espanol, entry desde el flujo de firma/`Mis créditos`.
- **No incluye:** backend (`E3-T17`/`E3-T18`/`E3-T19`/`E3-T20`), el simulador/solicitud/estado/firma
  (HU09-HU11) ni el panel web (`admin-web`). No implementa logica de negocio.

## Contexto embebido (decisiones que aplican)

- **Cliente delgado estricto** (`docs/19-ejecucion-dos-campos.md#4-cliente-delgado-estricto`,

  intereses, saldos ni mora; **muestra** lo que responde el backend (montos `*_minor` ya formateados
  por el servidor) y **envia** datos crudos.
- **Montos formato `S/ 9,999.99`** provistos por el backend; el cliente no calcula ni redondea
  (`docs/design/creditos-pantallas.md`, convenciones comunes).
- **4 estados obligatorios por pantalla** (`docs/20-diseno-ui.md#7-estados-obligatorios-por-pantalla`):
  contenido, cargando (skeleton), vacio (sin prestamos/cuotas), error accionable con Reintentar.
- **`POST .../pay` mueve dinero -> `ApiClient.postWithIdempotency`**; un reintento reutiliza la misma
  clave (`docs/19#4`). `PUT .../auto-debit` y las lecturas no llevan `Idempotency-Key`.
- **`PUT .../auto-debit`** no mueve dinero; el toggle solo refleja el estado devuelto por el servidor.
- **Estados de cuota del servidor** (`installment_status`): `Pendiente` (`PENDING`), `Parcial`
  (`PARTIAL`), `Pagada` (`PAID`), `Vencida` (`OVERDUE`); la UI muestra el estado TAL CUAL (sin
  reinterpretar).
- **Tema visual "Eucalipto y Ocre"** (`docs/20-diseno-ui.md#3-tokens-de-color`,
  `docs/design/design.md`); badges de estado con `success-container`/`warning-container`/
  `error-container` (mismo set que las pantallas de créditos ya existentes).
- **Sin PII/secretos** en disco ni en logs (regla 7); sin `Idempotency-Key` en lecturas.

## Modelo de datos

Sin persistencia local de dinero ni secretos. Estado efimero: `loan_id`, cronograma recibido,
estado de carga/error, flag de debito automatico. Modelos Dart de respuesta (del backend):
`Loan` (`id`, `application_id`, `account_masked`, `principal_minor`, `outstanding_principal_minor`,
`term_months`, `status`, `auto_debit_enabled`, `disbursed_at`) y `LoanInstallment`
(`installment_no`, `due_date`, `principal_minor`, `interest_minor`, `insurance_minor`,
`total_minor`, `status`, `paid_at`). No guardar PII en disco.

## API / eventos

- **Endpoints consumidos:**
  - `GET /credits/loans` (prestamos del titular).
  - `GET /credits/loans/{id}/schedule` (cronograma definitivo).
  - `PUT /credits/loans/{id}/auto-debit` (`{enabled}`; sin `Idempotency-Key`).
  - `POST /credits/loans/{id}/pay` (`Idempotency-Key`; body `{schedule_id?}`).
- **Eventos emitidos/consumidos:** ninguno (cliente).
- **Errores de negocio a mapear:** `NOT_FOUND` (neutro), `CONFLICT` (cuota ya pagada / prestamo no
  activo), `INSUFFICIENT_FUNDS` (`REJECTED`: mostrar saldo insuficiente, no error tecnico),
  `VALIDATION_ERROR`, errores de red `Reintentar`.

## Reglas de negocio

- El cronograma y el estado de cada cuota se muestran TAL CUAL el backend; el cliente no calcula
  cuotas/mora/saldos ni decide elegibilidad.
- El toggle de debito automatico refleja y persiste `auto_debit_enabled` del servidor; no simula el
  cobro.
- El pago manual de una cuota solo se ofrece para cuotas `Pendiente`/`Parcial`/`Vencida`; una cuota
  `Pagada` no muestra CTA de pago.
- `INSUFFICIENT_FUNDS` se presenta como mensaje accionable (no como error de sistema) y la cuota no
  cambia.
- 4 estados de UI y mensajes en espanol; sin logica offline.

## Criterios de aceptacion (CA)

- `CA-02` de HU12 (UI): se muestra el cronograma definitivo con fechas, montos por componente y
  estado por cuota; saldo de capital visible.
- `CA-03` de HU12 (UI): el cliente puede activar/desactivar el debito automatico de su prestamo y
  el estado se refleja tras confirmar el servidor.
- Pago manual de una cuota pendiente funciona (con `Idempotency-Key`), refleja la cuota `Pagada` y
  el nuevo saldo; `INSUFFICIENT_FUNDS` se comunica sin romper.
- 4 estados de UI y errores en espanol accionables.

## Regla de cliente delgado (dos campos)

La app solo solicita el cronograma/prestamos, muestra los datos y el estado que devuelve el backend,
y envia el toggle de debito automatico y el pago de cuota (con `Idempotency-Key`). No calcula cuotas,
intereses, mora ni saldos; no decide elegibilidad ni el resultado del cobro; no tiene logica offline.
El backend (`credits` -> `transactions` -> `ledger`) valida y contabiliza.
