## Objetivo

Construir el flujo Flutter de **billetera** (listado de vinculos enmascarados) y **vinculacion** de una
fuente de fondos (cuenta del banco o tarjeta), mostrando lo que devuelve el backend y enviando datos
crudos, con los 4 estados de UI y sin calcular ni decidir nada en el cliente.

## Alcance

- **Incluye:** pantallas en `frontend/lib/features/wallet/presentation/` para:
  (1) ver la **billetera** (`GET /wallet`) con sus vinculos (tipo, `last4`/`account_masked`, estado);
  (2) **vincular** una fuente de fondos (`POST /wallet/links`): elegir cuenta del banco (de las del
  titular) o tarjeta (datos crudos que el backend tokeniza);
  (3) estado del vinculo y mensajes en espanol. Servicio Dart sobre `ApiClient`, modelos de respuesta,
  4 estados (contenido/carga/vacio/error con Reintentar), entry desde la seccion de billetera.
- **No incluye:** backend (`E4-T01`), el pago express (`E4-T02`), el adaptador (`E4-T03`), la QA
  (`E4-T05`); QR (`E4-T06`+), el panel web (`admin-web`). No implementa logica de negocio.

  cargando (skeleton), vacio (sin vinculos), error accionable con Reintentar.
- **`POST /wallet/links` crea un recurso** -> `ApiClient` con `Idempotency-Key` (opcional segun
  `E4-T01`); un reintento reutiliza la misma clave.
- **Tema visual "Eucalipto y Ocre"** (`docs/20#3-tokens-de-color`, `docs/design/design.md`); badges de

## Modelo de datos

Sin persistencia local de dinero ni secretos. Estado efimero: vinculos recibidos, estado de
carga/error, formulario de alta. Modelos Dart de respuesta (del backend):
`Wallet` (`wallet_id`, `status`, `links: [WalletLink]`), `WalletLink` (`link_id`, `type`, `last4?`,
`account_masked?`, `brand?`, `status`, `linked_at`). No guardar PAN ni numeros completos.

## API / eventos

- **Endpoints consumidos:**
  - `GET /wallet` (billetera del titular).
  - `POST /wallet/links` (vincular; `Idempotency-Key`).
- **Eventos emitidos/consumidos:** ninguno (cliente).
- **Errores de negocio a mapear:** `NOT_FOUND` (neutro), `DUPLICATE_LINK`/`CONFLICT` (`409`), 
  `VALIDATION_ERROR` (`422`), `IDEMPOTENCY_CONFLICT` (`409`), errores de red `Reintentar`.

## Reglas de negocio

- Solo se muestran vinculos del titular (el backend aplica el aislamiento); la UI no cruza datos.
- La UI **no** calcula saldos/limites ni decide si un vinculo es valido; refleja el estado del backend.
- Solo se muestran datos enmascarados (`last4`/`****1234`); el numero completo nunca se almacena ni se
  muestra.
- 4 estados de UI y mensajes en espanol; sin logica offline.

## Criterios de aceptacion (CA)

- `CA-01` de HU13 (UI): el cliente puede vincular una cuenta del banco o una tarjeta y ver la billetera
  con el vinculo enmascarado `ACTIVE`.
- 4 estados de UI y errores en espanol accionables.
- Los valores mostrados son los del backend (sin recalculo del cliente); nunca se muestra ni persiste
  el PAN/numero completo.
- Reintento de vinculacion reutiliza la misma `Idempotency-Key` (sin duplicar).

## Pruebas requeridas

- Camino feliz: cargar billetera -> vincular cuenta (servicios mockeados) -> el vinculo aparece
  enmascarado; vincular tarjeta envia datos crudos y muestra `last4`.
- Errores: `404`/`409`/`422` mapeados a mensajes accionables; red -> Reintentar.
- Estados vacio/carga/error con Reintentar.
- No recalculo: los valores mostrados son los del mock del backend.
- Seguridad: el formulario no persiste el PAN; los logs no lo incluyen.

## Regla de cliente delgado (dos campos)

La app solo solicita la billetera, muestra los vinculos que devuelve el backend y envia los datos
crudos de la fuente de fondos (con `Idempotency-Key`). No tokeniza, no valida la cuenta, no calcula
limites ni decide elegibilidad. El backend (`wallet` + fachada de `accounts`) valida, tokeniza y
persiste; el PAN nunca sale del backend mas alla del request de alta.
